# AISS — Database Migration Guide (Alembic)

## Overview

Alembic is initialized against `core/models.py` (ORM tables: `users`, `threat_logs`,
`blocked_ips`, `system_events`, `scan_results`) and auto-reads `DATABASE_URL` from `.env`.

The raw `threats` table is managed by `core/database.py` directly (not via Alembic ORM),
so it does not appear in autogenerated migrations.

---

## Initial Setup (already done)

```bash
# Already run — do not re-run
alembic init alembic
alembic revision --autogenerate -m "initial_schema"
```

---

## Apply Migrations

```bash
# Apply all pending migrations to your database
alembic upgrade head

# Apply one step at a time
alembic upgrade +1

# Check current revision
alembic current

# View migration history
alembic history --verbose
```

---

## Create a New Migration (after changing models)

1. Edit `core/models.py` (add a column, new table, etc.)
2. Generate the migration:
   ```bash
   alembic revision --autogenerate -m "describe_your_change"
   ```
3. Review the generated file in `alembic/versions/`
4. Apply it:
   ```bash
   alembic upgrade head
   ```

---

## Rollback

```bash
# Roll back one migration
alembic downgrade -1

# Roll back to a specific revision
alembic downgrade <revision_id>

# Roll back everything
alembic downgrade base
```

---

## Database Switch

To switch from SQLite → MySQL, update `.env`:

```
DATABASE_URL=mysql+aiomysql://user:password@localhost:3306/aiss_db
```

Then run migrations against the new DB. Alembic auto-converts the URL to use
a sync driver (`pymysql`) for migration operations.

---

## Notes

- `alembic.ini` sets `sqlalchemy.url` to SQLite as default; the `env.py` overrides
  this at runtime from `DATABASE_URL` in `.env`
- The `threats` table is handled separately by `core/database.py` — do not add it
  to ORM models or Alembic will try to drop/recreate it
- Always backup your database before running `upgrade head` in production
